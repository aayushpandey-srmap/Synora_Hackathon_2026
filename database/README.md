# Auction database layer

## Architecture

Redis is the hot-path state store for an active auction. A Lua transaction atomically validates and applies a bid to the current price and leader keys, then publishes one update event. PostgreSQL is the durable system of record: it stores users, auction definitions, the immutable bid ledger, and the final settlement result written by the expiry worker.

The schema uses UUID primary keys for `users` and `auctions`, which are safe to expose and can be generated by independent writers. The append-only `bids` ledger uses an identity `BIGINT`; its compact, monotonically increasing key improves index locality and append throughput. If globally generated IDs are required before insertion, replace the bid identity with a UUIDv7 generated at the application boundary.

Each auction has many bids, and each user can place many bids. `bids.auction_id` and `bids.user_id` are restrictive foreign keys so historical audit rows cannot be orphaned. `auctions.winner_id` references the settling user and is nullable until settlement. The partial unique winner index permits at most one winning bid per auction.

Integrity is enforced at the database boundary: lowercased non-empty emails are unique, money values use `NUMERIC(12,2)`, bid amounts are positive, auction windows are ordered, and a settled auction must have both a final price and winner. `ON DELETE RESTRICT` preserves the audit trail.

The indexes are deliberately workload-specific:

- `idx_auctions_active` is a partial B-tree for active-page reads and expiry scans.
- `idx_auctions_status_start_time` supports lifecycle-filtered, newest-first auction pages.
- `idx_bids_auction_amount` supports leaderboard and winner verification queries.
- `idx_bids_user_id` and `idx_bids_auction_id` support foreign-key checks and history access.
- `idx_bids_auction_placed_at` supports chronological settlement/audit scans.

`schema.sql` enables `pgcrypto` before using `gen_random_uuid()`; the extension is included so the bootstrap script is self-contained:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

## Redis key and event specification

All `{id}` values are canonical lowercase UUID strings. Keys are scoped to an auction and must not be reused for a different auction.

| Key or channel | Redis type | Value | TTL policy |
| --- | --- | --- | --- |
| `auction:{id}:price` | String | Decimal amount encoded as an ASCII string, e.g. `125.50` | Set on first activation; expire at `end_time + settlement_grace`. The settlement worker may delete it after PostgreSQL settlement is durable. |
| `auction:{id}:leader` | String | Winning user UUID encoded as a string | Same TTL as the price key; must be updated atomically with the price. |
| `auction:{id}:status` | String | Lifecycle state for the auction, for example `ACTIVE`, `CLOSED`, or `SETTLED` | TTL is set to the remaining auction lifetime plus the settlement grace window so the worker can reconcile and then clean it up. |
| `auction:{id}:updates` | Pub/Sub channel | JSON event payload containing auction ID, price, leader ID, and event timestamp | Pub/Sub channels have no retained TTL or history. Consumers needing replay must use PostgreSQL or a separate stream (not this channel). |

The price and leader keys are a consistency pair: all writes must occur through the same Lua script, and readers should treat either key being absent as “auction state unavailable/expired,” not as a zero price. The script should reject bids unless the new amount is strictly greater than the stored price and should publish only after both keys have been updated.

Recommended `settlement_grace` is long enough for worker retries and clock skew (for example, 15 minutes). Redis expiry is a cleanup mechanism, not the settlement authority; `end_time` and the PostgreSQL settlement transaction remain authoritative.
